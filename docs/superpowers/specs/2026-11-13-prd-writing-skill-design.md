# PRD 写作辅助 Skill 设计

## 目标与范围

创建一个可由 Codex 与 Claude Code 自动发现的通用 skill，帮助产品经理及跨职能团队把产品想法转化为可评审、可设计、可验证的完整需求文档，或提升已有需求材料的完整性与可执行性。两种工具共用同一份核心指令与参考资料，按平台分别安装到 `.agents/skills/` 或 `.claude/skills/`；Codex 专属元数据仅作为可选配置保留。

每次完整流程都必须交付三份文档：PRD、产品设计文档、测试文档。不得只交付 PRD，也不得因信息不足而省略另外两份；无法确定的内容应以明确的假设、约束或待确认项表达。Skill 面向通用产品与 AI 产品。通用工作流保持一致；仅当 AI 能力会影响产品结果时，才加载 AI 专项要求。用户可以选择先在对话中迭代再定稿，或直接生成文档。默认行为是先做必要的自适应澄清，再完成并交付三份 Markdown 文档。

## 用户与主要场景

- 从零梳理一般软件或服务产品的需求并形成 PRD。
- 基于同一组产品决策，补齐与 PRD 配套的产品设计文档和测试文档，形成可交接的完整文档包。
- 从零梳理包含 AI 能力的产品需求，补足模型能力、数据、评测、降级及安全边界。
- 审阅和完善已有 PRD，指出缺漏、冲突、歧义与不可验证要求，同时保留原有有效决策。
- 信息不完整时继续推进：优先追问高影响缺口；低风险信息可用明确标注的假设暂代。

## 必需交付物及边界

每个需求任务都必须完成以下三份文档。三份文档可以保存在同一 Markdown 文件的独立章节中，也可以拆成独立文件；优先沿用用户指定的交付形式和现有项目结构，但交付时必须能清楚区分三份文档。

- **PRD（做什么、为什么）：**说明问题、目标用户与场景、目标和非目标、范围、功能及非功能需求、成功指标、验收标准、依赖、风险和待确认事项。它记录产品要解决的问题及产品行为要求，不代替详细交互设计或测试步骤。
- **产品设计文档（如何解决）：**将 PRD 需求转化为用户流程、页面 / 状态、交互行为、业务规则、异常与边界处理，以及必要的内容、权限和可访问性约束。只描述有依据的产品设计决策；不臆造视觉稿、技术架构、接口、数据模型或实现方案。缺少必要输入时，照常完成文档并标注待设计 / 待确认事项及其影响。
- **测试文档（如何验证）：**定义测试范围、前置条件、测试场景 / 用例、操作或输入、预期结果，以及适用的非功能、兼容性、安全、AI 质量或降级验证。用例应能追溯到 PRD 需求和相关设计规则；需求尚未定稿时，标明对应假设或待确认决策，不伪造确定的预期结果。

三份文档共享同一套事实、决策、假设和待确认项。至少建立可读的需求标识或等效交叉引用，使每项范围内需求能映射到对应设计规则和验证方式；设计规则不能引入未经 PRD 说明或明确标记的新范围。生成后检查三份文档之间的范围、术语、规则、状态和验收口径一致。信息缺失时，写出当前可成立的内容并标注未决部分及其影响，而不是留空、虚构或省略整份文档。

## 工作流

1. 识别任务是新建 PRD 还是完善现稿；识别是否涉及 AI 能力；识别用户期望的交互节奏。用户已明确的信息不重复询问。
2. 新建时梳理产品目标、用户、场景与范围。完善时先理解原文结构和已有决策，再定位问题。
3. 对会显著影响范围、方案或验收的缺口进行自适应追问，每轮只问一个中性、聚焦的关键问题。
4. 用户要求直接成稿时，在可行范围内完成全部三份文档，并把未确认事项、假设和风险清楚标注；不把假设写成既定事实。
5. 先整理并稳定需求基线，起草 PRD；再依据 PRD 编写产品设计文档；最后依据需求基线和设计规则编写测试文档。完善现稿时保留有效决策，并准备主要变更摘要及尚待确认的问题。无论用户最初称其为“写 PRD”还是“完善需求”，完整流程的完成条件都是三份文档均已形成。
6. 在内部对全部三份文档及其关联进行一次对抗式质量审查，寻找相互矛盾、遗漏边界、无法验证的目标、未经证实的假设、设计偏离需求、测试未覆盖要求及可能的失败路径。该审查过程、内部推理和审查记录不展示给用户，也不写入交付文档。
7. 根据审查结果修订文档。只有会影响产品决策或阻碍执行的问题才以中性、可行动的“风险 / 待确认事项”呈现；不展示辩论过程或内部审查标签。最终检查三份文档齐全、互相一致、需求到设计与测试可追溯，以及清晰度、可实现性、可验证性和对既有决策的保真度。

### 自适应澄清规则

- 以一个会影响产品决策的未知点为起点，按需探索目标与实际场景、判断依据、关键假设、替代解释或取舍；不要求每次对话机械走完全部维度。
- 每轮只问一个问题。问题应开放、中性、聚焦，不暗示预设答案、不把建议包装成问题，也不将多个维度塞进一个长句。
- 根据回答选择下一步：澄清事实、检验证据、探查边界或确认决策影响。检视的是假设和依据，不是用户本人；已有充分依据时不反复追问。
- 当继续追问不太可能改变范围、优先级、方案或验收，且剩余未知可以作为假设 / 待确认事项记录时停止。用户要求停止、拒答或直接交付时立即停止提问。
- 在直接成稿模式下，若用户未禁止提问，只追问会阻塞合理成稿的高影响缺口；若用户明确说不要提问，则不追加问题，以显式假设和待确认事项继续。
- 提问方法保持隐含；用户可见的问题、PRD、产品设计文档、测试文档和交付说明中，不出现提问方法名称或对方法的说明。

## PRD 内容策略

优先沿用用户或团队提供的模板。没有模板时，按需求复杂度裁剪通用骨架，覆盖：

- 产品背景与问题
- 目标用户与关键场景
- 产品目标、非目标和范围
- 核心流程与功能要求
- 异常情况与重要边界
- 必要的非功能要求
- 成功指标及其统计口径
- 可判定通过与否的验收标准
- 依赖、风险和待确认事项

不要为了填满模板而加入不相关章节。小需求可压缩结构，复杂需求可以展开。

### AI 专项

仅在 AI 能力与产品结果相关时纳入适用内容：能力边界、输入输出约束、数据来源与隐私要求、效果评测与上线门槛、失败降级或人工接管、安全风险。未知的模型或技术决策应列为待确认事项，不擅自指定。

AI 专项应贯穿三份文档：PRD 写明能力与风险要求，产品设计文档写明用户如何使用、确认、纠错或接管，测试文档写明质量评估、边界 / 失败场景及上线门槛验证。只纳入适用内容，不复制无关清单。

## 技能包结构

```text
prd-writing/
├── SKILL.md
└── references/
    ├── prd-structure.md
    ├── product-design-structure.md
    ├── test-document-structure.md
    ├── ai-product-checklist.md
    └── visual-design-research.md
```

`SKILL.md` 负责入口识别、工作流、追问、三份文档的共同交付要求与一致性检查。核心 frontmatter 仅使用两种工具均支持的 `name` 和 `description`，参考资料使用相对路径。Codex 从 `.agents/skills/prd-writing/` 发现技能；Claude Code 从 `.claude/skills/prd-writing/` 发现技能。仓库以 `.agents/skills/prd-writing/` 为唯一维护源，README 提供复制到 Claude Code 项目级或用户级目录的安装方式，不维护重复副本。`agents/openai.yaml` 是 Codex 专属的可选元数据，Claude Code 不依赖它。`prd-structure.md`、`product-design-structure.md` 和 `test-document-structure.md` 分别说明三份文档的职责、结构和裁剪原则；`ai-product-checklist.md` 说明 AI 专项的适用条件及其在三份文档中的映射；`visual-design-research.md` 仅在用户界面视觉方向属于设计范围时，指导检索和转译 Refero Styles 等具体参考，不把参考库首页当作设计规范。首版不加入脚本或示例库；只有重复使用或验证中出现明确需求时再考虑扩展。

## 质量原则

- 把事实、假设、建议和待确认事项区分开。
- 澄清问题应当帮助用户检验决策依据，不诱导用户接受模型偏好的方案。
- 需求说明触发条件、预期行为及重要边界。
- 指标说明口径；验收标准能够客观判断通过与否。
- 发现需求间冲突时明确指出，避免替用户静默决策。
- 改写时保留已有有效信息和决策，并说明关键变更。

## 验收计划

### 结构验收

- 使用 skill validator 检查 frontmatter、skill 命名及脚手架占位内容；另行核对主文件中的参考文件链接均指向实际存在的文件。
- 检查技能描述是否准确且有区分度，`SKILL.md` 是否足够精简，参考材料是否按需加载。
- 确认自适应澄清与内部审查规则放在主工作流或精简参考资料中，不将澄清扩展成固定长问卷；面向用户的提问和交付物不暴露方法名称。
- 确认 Refero 只在涉及界面视觉方向时触发；具体视觉规则须基于可访问的样式条目，而非从 Refero 首页、标题或缩略图推断。
- 确认相同的核心 `SKILL.md` 和参考资料可分别放入 Codex 与 Claude Code 的发现目录；平台安装说明与各自调用方式正确，Claude Code 不依赖 `agents/openai.yaml`。

### 行为验收

按独立测试计划执行，详见 [PRD 写作 Skill 测试计划](2026-11-13-prd-writing-skill-test-plan.md)。核心通过标准是：每个用例均交付 PRD、产品设计文档和测试文档；三份文档基于同一事实与决策集，范围和规则一致，并具备需求到设计 / 测试的追溯关系。除此之外，问题须单一、中性且能推动关键决策；在有必要时能探查证据或假设，而非机械追问；不编造事实或覆盖已有决策；非 AI 产品不出现无关 AI 专项；内部审查过程不外显，但确有决策影响的问题会以中性、可行动的方式呈现。涉及视觉参考时，按测试计划 T09 验证其使用边界、来源记录、规则转译及访问失败时的处理。

## 非目标

- 首版不绑定特定行业或公司内部 PRD 模板。
- 首版不自动发布、同步或写入外部文档系统。
- 首版不替用户决定未提供的产品策略、模型选型或指标目标。
- 首版不包含脚本、应用界面或额外示例库。
