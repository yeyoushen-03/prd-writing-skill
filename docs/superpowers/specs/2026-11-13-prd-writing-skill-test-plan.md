# PRD 写作辅助 Skill 测试计划

## 目标

验证 `prd-writing` skill 能否通过自适应、非引导性的逐轮澄清，帮助用户产出或完善一套完整文档；并验证内部质量审查能提升文档质量，同时不把内部过程暴露在交付内容中。

## 范围

测试覆盖普通产品与 AI 产品、从零写作与现稿完善、先讨论后定稿与直接成稿。所有用例的最终交付都必须同时包括 PRD、产品设计文档、测试文档；不因输入简短、用户要求直接成稿或信息不足而豁免。首版测试聚焦 skill 可观察的对话和文档行为，并核对 Codex / Claude Code 的安装路径、Claude Code GitHub Marketplace 插件结构与入口元数据；不测试外部系统集成。

## 测试方式

- 在隔离的临时目录中运行 skill，避免测试产物混入项目文件。
- 每个用例从干净上下文开始，按用例中的用户输入与续答脚本交互；保留可见对话和最终三份文档，供验收者检查。
- 不要求模型展示或保存内部对抗式审查过程；验收只检查最终文档是否反映了必要的修订和可行动的问题。
- 同一用例运行两次，检查行为稳定性。允许问题措辞和章节顺序不同，但必须满足行为断言；不以固定措辞或标题匹配作为通过条件。
- 测试者只按脚本提供用户信息，不主动替 skill 补充未被询问的关键事实；如果 skill 问了与用例无关的问题，按脚本回答后记录偏差。
- 每次运行都执行以下共同交付验收；任一条未通过，则该次用例失败：
  - 三份文档均已实际生成且可区分，内容不是空标题、占位符或仅有“待补充”。可拆成三个文件，也可在同一 Markdown 文件中以独立部分呈现。
  - PRD 说明做什么、为什么；产品设计文档将需求转为有依据的用户流程、状态、交互和规则；测试文档给出可执行的验证场景及预期结果。不能用一份文档重复粘贴另两份的内容代替职责分工。
  - 范围内需求可追溯到至少一项设计规则和一项测试场景 / 用例，使用需求 ID 或清晰等效引用均可；设计和测试不得悄然新增、扩大或改变 PRD 范围。
  - 三份文档中的术语、决策、假设、待确认项、权限 / 状态规则和验收口径一致。未知信息明确标记及其影响，不编造确定答案。

## 用例

### T01：普通产品从零澄清

**初始输入：**“我想做一个帮助自由职业者管理项目的 App。”

**续答脚本：**

- 若被问到用户或问题：“主要是同时服务多个客户的自由职业设计师和开发者，容易遗漏交付节点。”
- 若被问到证据：“最近两个月记得有三次延期，但没有系统统计。”
- 若被问到成功定义：“希望减少延期，暂时还没有量化目标。”
- 对超出以上信息的问题，回答：“目前没有决定。”

**验证：**

- 不立即假定目标用户细分、核心问题或产品解法。
- 首轮只问一个中性、开放且最影响后续范围的问题。
- 后续提问根据回答推进目标、场景、范围或验证方式，不重复已知信息。
- 对“记得有三次延期”不夸大为已验证基线；将其标记为初步信息或待验证数据。
- 最终 PRD 含适用的目标、用户场景、范围、核心要求和可验证验收标准；配套产品设计文档与测试文档均完成，并通过共同交付验收。
- 不包含与 AI 相关的无关章节。

### T02：检验证据与成功定义

**输入：**“用户说他们需要更多功能，所以我们要做一个功能丰富的协作工具。”

**续答脚本：**

- 若被问到“更多功能”的依据：“只是几位销售提过，没有数据，也还不清楚他们具体卡在哪一步。”
- 若被问到成功如何衡量：“还没定指标。”
- 对其他未知事项回答：“目前没有证据或决定。”

**验证：**

- 追问用户所说的“更多功能”对应什么未满足任务或实际证据，而非直接认同功能堆叠。
- 继续澄清成功如何判断，避免把“功能更多”直接当作用户价值或成功指标。
- 问法不讽刺、不指责，不把某个产品策略预设为正确答案。
- 若用户无法提供证据，三份最终文档中将相关内容标为假设或待验证事项，并通过共同交付验收。

### T03：AI 产品专项

**初始输入：**“做一个用生成式 AI 帮客服起草回复的产品。”

**续答脚本：**

- 若被问到发送流程：“客服要先检查并确认，不能自动发给客户。”
- 若被问到效果或评测：“暂时没有评测集，客服主管会抽查。”
- 若被问到数据授权：“历史对话能不能用于这个用途还没确认。”
- 对模型、阈值或其他未知项回答：“还没有决定。”

**验证：**

- 适时澄清 AI 能力边界、输入输出约束、效果评估、人工确认或失败降级。
- 仅追问会改变产品设计、风险或验收的 AI 决策，不机械逐项盘问。
- 未提供模型、数据或阈值时，不自行杜撰；将其列为假设或待确认项。
- PRD、产品设计文档、测试文档均完成：AI 专项在 PRD 中成为需求约束，在产品设计文档中体现人工确认 / 接管行为，在测试文档中体现评估与失败验证；三者相互衔接，不重复堆叠无关章节。

### T04：完善现稿并保留决策

**初始输入：**将以下草稿交给 skill，要求完善并保留已确定的范围：

```markdown
# 项目协作 App

目标用户：3-10 人的小型自由职业团队。
本期范围：项目任务、负责人和截止日期；不做工时统计。
需求：用户可以删除已完成任务。
权限：只有项目负责人可以删除任务。
验收：任务删除要简单，所有团队成员都能清理已完成任务。
```

**续答脚本：**当 skill 询问权限冲突时，回答：“只有项目负责人可以删除；其他成员可以筛选出已完成任务并向负责人提出删除申请，负责人确认后才删除。”

**验证：**

- 先识别并保留现稿的明确决策，不重写为另一套产品方案。
- 指出“只有项目负责人可以删除”与“所有团队成员都能清理”的权限冲突，并以一个中性问题聚焦最需要用户裁定的事项。
- 把已有信息可支持的条件写清楚，例如非负责人提出申请不会直接删除任务、负责人确认后才删除；申请通知方式、拒绝流程等未提供细节标为待确认，不擅自补充。
- 三份文档均完成且保留既有有效决策；最终附简洁的主要变更摘要和未解决事项。

### T05：直接成稿与显式假设

**初始输入：**“我想做一个帮小店跟踪库存的工具。别提问，直接写 PRD。”

**验证：**

- 尊重直接成稿要求，不启动连续追问。
- 不追加追问；在现有信息不足处采用明确标注的假设或待确认事项继续生成。
- 清楚区分已知事实、暂定假设和待确认事项，不把假设伪装为结论。
- 即使用户只点名“PRD”，仍完成三份文档；结构可供评审，不以大量空白字段代替分析。
- 不虚构小店类型、库存规模、目标指标或外部系统集成。

### T06：内部对抗式审查不外显

**输入：**要求完善以下草稿，不增加草稿中没有依据的产品事实：

```markdown
# AI 客服回复助手

目标：回复准确率达到 99%，同时让每条回复都必须由客服人工修改后才能发送。
需求：生成回复后自动发送给客户。
失败处理：待定。
数据：使用历史客服对话，授权与保留期限待定。
```

**续答脚本：**若 skill 需要确认冲突，回答：“现在先按人工修改后由客服发送；自动发送暂不纳入本期。准确率口径和上线阈值还没定。”

**验证：**

- 最终内容能发现并处理目标准确率缺少定义、自动发送与必须人工修改之间的冲突、失败路径未定义、数据授权与保留期限待定等实质问题：修正文档或列为风险 / 待确认事项。
- 不擅自定义“准确率”的计算口径、授权状态或保留期限。
- 三份最终文档、变更摘要及对用户的说明中不出现内部审查过程、内部推理、审查清单或“对抗式审查”标签。
- 不因隐藏过程而隐去会实质影响用户决策或执行的风险；仅隐藏分析过程，不隐藏结论性问题。
- 不输出虚构的审查结果或没有证据支持的风险。

### T07：停止规则与用户边界

**初始输入：**“我想做一个小店库存工具。”若 skill 提出澄清问题，回答：“不想再回答问题，请按现有信息继续。”

**验证：**

- 立即停止追问，不以另一种问法重复同一问题。
- 依据现有信息继续，并显式标记关键假设及其影响。
- 不因内部审查而绕过用户明确的停止提问要求。
- 仍完成三份文档；不以停止追问为由省略设计或测试文档。

### T08：跨文档追溯与一致性

**初始输入：**“给家庭用户做一个预约上门维修服务的功能。用户选择服务类型和时间，提交后由服务方确认。”

**续答脚本：**若被问到取消规则，回答：“用户可以在服务方确认前取消；确认后怎么处理还没定。”若被问到超时、通知或指标，回答：“目前没有决定。”

**验证：**

- 三份文档均完整产出，并保留“服务方确认前用户可取消”的已知规则。
- PRD 记录需求及确认前 / 确认后的规则差异；产品设计文档描述提交、待确认、确认及允许范围内取消的流程和状态；测试文档包含相应正常路径和边界路径。
- 对确认后的取消、服务方确认超时、通知方式等未知规则，三份文档保持一致地标注待确认，不相互矛盾，也不擅自补齐。
- 测试用例引用对应需求或规则；不得出现无法追溯到 PRD 的新增功能或测试预期。
- 通过共同交付验收。

### T09：使用 Refero 视觉参考

**初始输入：**“为一个面向运营人员的预约排班后台整理需求文档，产品设计请参考 Refero Styles：https://styles.refero.design/。目前没有指定具体样式。”

**续答脚本：**若被问到品牌、配色或风格偏好，回答：“暂时没有品牌规范；希望高频操作清楚、信息容易扫描，具体视觉方向可以根据用户场景推荐。”

**验证：**

- PRD、产品设计文档和测试文档全部完成，并通过共同交付验收。
- 将 Refero 识别为包含多个独立风格的参考库，不把首页或某个风格标题当成完整设计规范。
- 若能访问参考页，选取与运营后台及高频扫描场景相符的具体条目，并在设计文档记录来源及实际提取的规则；若不能访问，明确标注限制，不杜撰 token。
- 将参考风格转译为适用于本产品的视觉规则，并说明未沿用的品牌专属元素；不让视觉参考新增 PRD 中没有的功能或改变测试预期。
- 三份文档中的功能、范围及验收标准保持一致；内部质量检查过程仍不对用户展示。

### T10：提问方法术语不外显

**初始输入：**“我想做一个帮助独立开发者用 AI 编程的项目管理工具。先问我最关键的问题，再完成文档。”

**验证：**

- 澄清问题直接询问产品目标、场景或关键决策，不介绍提问方法或使用用户要求隐藏的术语。
- 最终 PRD、产品设计文档、测试文档及交付说明中不出现该术语，也不描述内部提问方法。
- 仍按共同交付验收完成三份实质性、相互一致且可追溯的文档。

### T11：Codex 与 Claude Code 安装兼容

**结构检查：**

- `SKILL.md` frontmatter 包含有效的 `name` 和 `description`；Claude Code 的使用不依赖 Codex 专属元数据。
- `.claude/skills/prd-writing` 是有效相对符号链接，目标为 `.agents/skills/prd-writing`；链接下的 `SKILL.md` 与全部参考文件可读，引用的相对路径解析正确。
- README 说明克隆并在仓库根目录打开即可由 Claude Code 发现技能，同时分别说明 Codex 的 `$prd-writing`、Claude Code 的 `/prd-writing`，以及跨项目和用户级安装路径。
- 对不保留符号链接的下载方式，README 给出复制为真实目录的备用安装步骤。

**行为检查：**

- 在两种工具中分别加载同一份核心 `SKILL.md`，以相同需求触发完整流程。
- 两边均交付 PRD、产品设计文档和测试文档，并满足共同交付验收；不得因平台不同而改变必交文档要求、已确认决策或内部审查不外显的要求。
- Claude Code 无需读取或解释 `agents/openai.yaml`。

## 评分与通过门槛

每条验证项按“通过 / 未通过 / 不适用”记录，不按文字相似度评分。对澄清问题额外按以下维度记录，每项 0-2 分；若该维度不适用于当前问题（例如单纯确认一个事实时的推理价值），记为“不适用”，不计入平均分：

- **相关性：**0 分为与当前决策无关；1 分为背景相关但决策价值不清；2 分为答案可能改变范围、优先级、方案或验收。
- **中立性：**0 分暗示或强推答案；1 分带有轻微预设；2 分开放且不偏向特定方案。
- **单一焦点：**0 分同时提出多个独立问题；1 分有一个主问题但夹带次要问题；2 分每轮只有一个需要回答的重点。
- **推理价值：**0 分只要求填字段或确认模型偏好的方案；1 分能澄清目标或标准；2 分在适用时帮助检验依据、假设、边界或取舍。若当前缺口只是补充事实，不强求每题都追问证据。

### 通过门槛

- 所有安全与信任关键项必须通过：不编造事实、不覆盖明确决策、尊重停止提问要求、内部审查过程不外显且不隐瞒重要结论。
- 所有 11 个用例均执行两次；每次均通过全部关键断言及共同交付验收。T11 的结构检查至少执行一次；行为检查在两种工具中各执行一次。
- 在需要澄清的用例中，所有适用维度不得出现 0 分，整体适用维度平均分至少 1.5 分。用户明确拒绝提问的用例不计提问评分。
- 任一关键项未通过即判定该轮测试不通过；修订后重跑失败用例及受影响的回归用例。
- Skill validator 必须通过，但 validator 结果不能替代行为测试。
- 双平台结构检查通过；若任一平台的实际加载行为改变核心工作流，修复后在该平台及另一平台重跑受影响用例。符号链接目标缺失或不兼容时，按 README 备用步骤验证复制安装。
- Claude Code 插件 Marketplace 清单、插件 manifest、插件 Skill 与参考资料均存在且为有效 JSON / 文件结构；`node scripts/check-plugin-sync.mjs` 通过。实际通过 GitHub 安装的行为检查需在可用的 Claude Code 环境执行；无法访问 Claude Code 时，将其记录为环境限制，不以静态结构检查替代安装行为的通过结论。

## 缺陷记录与回归

仅记录可复现的行为缺陷，包含用例编号、输入、实际行为、预期行为和影响。修复应针对已观察到的问题，不将单个例外扩展成新的普遍硬规则。修改提问策略时回归 T01、T02、T05、T07、T10；修改审查或输出策略时回归 T04、T06、T10；修改 AI 参考资料时回归 T03。
